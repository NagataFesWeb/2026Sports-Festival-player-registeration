# セキュリティ・個人情報保護仕様

## 1. 基本方針

本システムは氏名・学籍番号・クラス・出場競技を扱う。管理スプレッドシートと名簿は外部公開せず、体育祭スタッフ専用の共有Gmailアカウントで所有し、必要最小限の相手だけに共有する。

## 2. 権限

### 招集パート

- 管理画面閲覧
- 申請詳細閲覧
- 修正、保留、却下
- 承認して正式反映
- 帳票閲覧・PDF出力

本番モードへの切替時に、実行した体育祭スタッフ共有Gmailアカウントを`AUTHORIZED_EDITOR_EMAILS`の担当者として登録する。原則としてこの1アカウントだけを操作とシステムシートの編集許可対象にする。本番モードでは担当者一覧を必須とする。

### 担当教員

- 招集パートと同等以上
- 生徒マスター差し替え
- 権限設定
- 障害時の復元

### クラス代表者

- フォーム回答のみ
- 管理ファイル、正式名簿、生徒マスターは閲覧不可

### claspによる開発検証

- Apps Script Execution APIは`MYSELF`に限定し、ログイン中の開発者本人だけが検証関数を実行できる。
- 検証関数は個人情報やフォーム回答を返さず、設定の選択範囲・件数・成功可否だけを返す。
- 公開Webアプリや匿名アクセスは作成しない。

## 3. 共有設定

- 管理ファイルの所有・実行は体育祭スタッフ共有Gmailアカウントに統一する。
- 共有アカウントの復旧先、2段階認証手段、認証情報の保管責任者を校内で記録する。
- ファイル共有は必要な閲覧者・編集者だけに限定する。
- `リンクを知っている全員`は禁止する。
- 本番切替時とメニューの`管理ファイルの共有範囲を点検`で、管理スプレッドシートと選手名簿フォルダ以下を確認する。不特定多数・リンク共有・ドメイン共有があれば本番切替を止める。
- 選手名簿の作成処理から共有権限を追加・拡大しない。保存先フォルダの既存権限だけを使用する。
- フォーム回答者へ生徒マスターを共有しない。

## 4. LLM・開発制限

- 実在の氏名、学籍番号、メールアドレス、回答内容をLLMへ送らない。
- 実在データのスクリーンショットをLLMへ送らない。
- 開発・テストでは疑似生徒マスターを使用する。
- 本番用`生徒マスター`の実在データはスプレッドシート内だけで入力・利用し、リポジトリ、テスト、通常ログ、LLMへ複製しない。切り替え検証には架空データだけを使う。
- GASからLLM APIを呼び出さない。
- 外部API送信を避けるため`UrlFetchApp`を原則禁止する。
- 例外として、フォーム作成を高速化する目的に限り、固定の`https://forms.googleapis.com/v1/forms/{formId}:batchUpdate`へフォームの設問定義を送信できる。送信内容は設問名、選択肢、必須設定、分岐先、表示順だけとし、生徒マスター、フォーム回答、氏名・学籍番号の入力値、メールアドレス、正式登録データ、帳票本文を含めない。
- Forms API呼び出しを実装する関数は、競技設定とフォームIDだけを受け取り、生徒・申請・回答型を引数に持たない。URLはソース内の固定Google公式エンドポイントとし、任意URLを指定できる設定を設けない。
- API要求本文・応答本文をログへ出力しない。HTTPエラーは状態コードとPC初心者向けの対処だけを画面へ表示する。
- フォームのファイル移動には`DriveApp`、回答取込には標準のフォーム送信トリガーを使用する。Forms APIは回答の読取・送信・更新には使用しない。
- フォーム再生成時は、新フォームの作成に成功してから旧フォームの送信トリガーを削除し、旧フォームをゴミ箱へ移動する。
- 分割作成中の新フォームには回答送信トリガーを設定せず、作成完了時にだけ設定する。中断・取り消し・実行時間超過では現在使用中のフォームを変更しない。

## 5. ログ

通常ログに記録可能:

- 申請ID
- 内部エラーコード
- 実行日時
- 処理結果
- ファイルIDのハッシュまたは論理名

通常ログへ記録しない:

- 氏名
- 学籍番号
- メールアドレス
- 名簿本文
- フォーム回答本文

業務上必要な変更履歴はアクセス制限された`変更履歴`シートへ保存する。

## 6. 外部通知

- メール本文へ名簿全体を記載しない。
- 申請内容の修正は管理サイドバー内で行い、変更前後・理由・実行者・日時を変更履歴へ保存する。
- 氏名を含める必要がある場合は担当教員の承認を得る運用とする。

## 7. バックアップ・復旧

- 正式反映前に管理データのバックアップを作成する。
- 名簿の版名、保存先、作成者、作成日時、登録件数を`選手名簿作成履歴`へ保存する。
- 帳票更新失敗時に更新前版へ戻せること。
- 変更履歴は一般利用者が削除できないこと。
- `承認待ち`、`申請項目`、`検査結果`、`登録データ`、`承認履歴`、`変更履歴`、`フォーム回答原本`等にはシート保護を設定する。担当者一覧がない環境では警告保護とし、通常操作を継続できるようにする。
- 開発用疑似データの削除では、`mock-response-数値`に結び付いた疑似の承認履歴・変更履歴だけを削除できる。履歴シート全体を削除する操作は設けない。
- Google Sheetsの版履歴を補助的復旧手段として使用する。
- 長時間の名簿作成は1ファイルずつ時間主導トリガーで実行する。Document Propertiesへは進捗とファイル識別情報だけを保存し、氏名・学籍番号・フォーム回答を保存しない。
- 作成途中の登録スナップショットは管理スプレッドシート内の非表示シートに限定し、完了または取り消し時に削除する。
- 本番開始後の疑似データ練習は、本番ファイル内では行わず`練習用コピーを作成`で分離した専用コピーを使用する。
- 練習用コピーでは本番フォームID、実回答、登録データ、履歴、生徒マスターを消去し、専用フォルダ内で新しく作ったフォームだけを停止・削除できる。
- 練習用コピーを本番モードへ変更する操作は禁止する。

## 8. 受け入れ条件

- フォーム送信だけでは正式データが変更されない。
- クラス代表者が管理ファイルを閲覧できない。
- 管理スプレッドシートと選手名簿に不特定多数への共有がないことを自動点検し、500件を超えた残りだけ管理者が手動確認する。
- 実データを使わずに主要テストを完了できる。
- 通常ログに氏名・学籍番号が出力されない。
- フォーム送信トリガーは作成者の権限で動作し、正式データ・帳票を更新しない。
- HTMLサイドバーから呼ぶ関数は`src/main.ts`の公開関数からビルド時に自動抽出し、入口関数の登録漏れを防ぐ。
