# フォーム・競技・ルール設定

## 正本と生成物

設定の正本は管理スプレッドシートの`競技設定`、`フォーム設計`、`ルール設定`とする。Googleフォームは年度ごとに設定から新規生成する派生物であり、競技項目をフォーム画面で直接追加・削除しない。

`フォーム設計`の`締切`は日本標準時の日付セルとする。利用者はセルをクリックしてカレンダーから選択し、時刻や曜日を手入力しない。表示とGoogleフォームの説明は`yyyy/MM/dd(曜)`（例：`2026/09/13(日)`）とし、曜日は日付から自動計算する。従来の`yyyy/MM/dd HH:mm`形式が残っている場合は日付部分を読み取り、カレンダー入力セルへ自動移行する。

`フォーム項目対応表`は生成時にGASが作成し、表示名ではなく`event_id`と`field_key`で質問を識別する。設定変更やフォーム生成だけでは、`登録データ`や帳票を変更しない。

## 今回の実装範囲（優先度A）

- `設定画面`、`競技設定`、`フォーム設計`、`ルール設定`、`フォーム項目対応表`、`設定点検結果`を作成する。
- `フォーム設計`は`年度`から`フォーム保存フォルダURL`までの16行を正本の並びとする。行が削除されている場合は、`設定シートを作成・不足分を補う`と`設定を点検`が、入力済みの値を保ったまま不足行を既定値で補う。点検が示す行番号は固定値ではなく、シート上の実際の行から求める。
- `疑似データ設定`シートの行は`項目`・`値`・`説明`の3列で、行番号を直書きせず`ensureMockDataSettings`の`settingRows`配列から背景色・入力規則の位置を計算する。行を足しても既存行の書式がずれない。
- `疑似データ設定`に`疑似申請に使う名簿`（プルダウン、既定`疑似生徒マスター`）と`疑似申請を作成した名簿`（自動記録、編集不可）を置く。前者は疑似申請の選手をどちらの名簿から選ぶかを決め、後者は作成時の名簿を記録して、後から選択を変えたときの食い違いを検出するために使う。
- 旧版のブックには名簿行が無いため、初回だけ「本番用`生徒マスター`に入力があれば`生徒マスター`」という以前の挙動と同じ初期値を書き込む。以後はこの行の値が正になる。
- 開発用に`疑似データ設定`を作成し、対象学年・対象クラスをチェックボックスで選べるようにする。選択範囲の疑似生徒数を疑似申請数として自動計算し、問題を含む申請数もコード変更なしで調整できるようにする。
- 疑似データ生成では`ルール設定`の論理式を読まない。同じ競技内で同じ生徒を重複させないことと、クラス全体でできるだけ均等に割り当てることだけを守り、登録枠が生徒数を超えるときだけ必要な回数だけ重複させる。生成予定の全申請を保存前に検査し、指定件数以外の警告・エラーが見つかった場合は既存データを置き換えない。設定した論理式を満たせない場合は、対象と件数を示して停止する。
- `欠員許可=TRUE`の競技では、割り当てられる生徒がいない枠を`出場しない`にする。競技ごとに欠員数を警告1件へまとめ、疑似データ作成は続行する。`欠員許可=FALSE`の枠を埋められない場合に限りエラーで停止する。
- 疑似の2026年度設定を初期値として作成する。既存の設定行は初期化で上書きしない。
- `設定を点検`で重複ID、必須項目、必要人数、対象学年、表示順、存在しない対象競技IDを検査する。
- `表示順`は名簿の並び順に加えて、種目別名簿・当日変更用名簿のページ分けと、**修正フォームのセクション（ページ）分け**にも使う。100で割った商が同じ競技は、名簿では1枚のシートへ、修正フォームでは1つのページへまとまる。学年ごとに分けた競技を1枚に載せたい場合は301・302・303のように連番にし、別のページにしたい場合は100・200・300のように100刻みにする。
- 名簿のページと修正フォームのセクションは同じ区切りを使う（`displayOrderBlockKey`）。片方だけを変えることはできないので、番号を振り直すときは両方の見え方を確認する。
- 競技数の多いまとまり（棒引き12チーム、騎馬9騎など）は、必ず同じ100番台へ収める。500・510・520のように10刻みで振ると16競技目が600番台へはみ出し、修正フォームでは1つのまとまりが2ページへ分かれる。分かれたことは画面に出ないので、`=FLOOR(表示順/100)`を隣の列へ入れて、まとまりごとに同じ値になっているか確かめる。
- `ルール設定`の対象競技は、現在年度の`競技設定`で有効な競技からチェックボックス列を自動生成する。1つのルールで複数競技を選択できる。
- 競技の追加・名称変更・無効化後にルール設定を開くか設定点検を実行すると、`event_id`をキーに対象列を同期する。名称変更では選択を保持し、無効競技の列は外す。
- エラーは対象シート・行・直し方を日本語で表示する。
- 未使用の空白行は、チェックボックスに`FALSE`が入っていても検査対象にしない。
- `ルール設定`の使用中判定には、利用者が直接入力する`rule_id`、`ルール名`、`判定`、`表示メッセージ`、`備考`、`論理式`と、`有効`のチェックだけを使う。自動生成される`対象`・`対象event_id`と、非表示の互換列`旧条件`・`旧上限`だけが残った行や、対象競技のチェックだけが残った行は、見た目が空白なら未使用行として検査しない。`有効`にチェックがある行は空白でも検査する。
- 検査結果の行番号は、未使用行を除外したあともシート上の実際の行番号を表示する。
- 有効な競技の`必要人数 × 対象学年のクラス数`を合計し、生徒マスター人数より少ない場合と、多い場合の両方で差分人数を警告する。少ない場合は未出場者、多い場合は同一生徒の複数競技参加または必要人数の設定誤りを確認する。運用上正しい場合は警告を確認して下書き作成を続けられる。
- エラー0件の場合だけ、通常登録フォームと修正申請フォームを非公開の下書きとして新規生成する。
- 通常フォームは学年分岐を持ち、全学年競技と該当学年の競技だけを各学年ページへ生成する。
- 有効な競技だけを生成し、必要人数、走順、欠員許可から質問を作る。
- 修正申請フォームの競技一覧も有効な競技設定から生成する。
- 修正申請フォームは1回答につき1競技を選び、その競技の全枠を入力する分岐形式で生成する。
- 各質問の`form_id`、`item_id`、`field_key`、`event_id`を`フォーム項目対応表`へ保存する。
- 管理スプレッドシートが置かれているフォルダ内に`forms`フォルダを作り、生成した通常・修正フォームを保存する。既存の`forms`フォルダがあれば再利用する。
- 各生成フォームへ回答送信トリガーを設定する。
- 通常・修正フォームに生成するすべての学籍番号欄へ、半角数字4桁の回答検証と「4ケタの学籍番号を数値で入力してください」のエラー表示を設定する。

## 論理式ルール

全変数、演算子、優先順位、設定例、使用できない書き方は[ルール論理式の完全ガイド](rule-expression-guide.md)を参照する。

ルールはすべて`論理式（TRUEなら問題なし）`列へ入力する。式がTRUEなら問題なし、FALSEなら`判定`列に従ってエラーまたは警告を1件追加する。対象は右側の競技チェック欄で選ぶ。`有効`にチェックがあり論理式が空欄の行は設定エラーとする。

非表示の`旧条件（互換）`・`旧上限（互換）`列は読み取らない。以前はこの列のキーワードからシステムが内部でルールを解釈していたが、その処理は廃止した。既存データを消さないため列は残すが、何を書いても動作は変わらない。重複の上限は`MAX_PER_EVENT <= 1`や`MAX_PER_STUDENT <= 2`のように論理式で書く。

### ルール設定で変えられない常時チェック

次の検査は入力そのものの確認であり、`ルール設定`の行を消しても無効にできない。どの枠かを行単位で表示する。判定の重さは表のとおりで、`STUDENT_NOT_FOUND`だけが警告である。

| 検査 | 内部コード | 判定 |
|---|---|---|
| 学籍番号が未入力 | `STUDENT_ID_MISSING` | エラー |
| 学籍番号が半角数字4桁でない | `STUDENT_ID_INVALID` | エラー |
| 生徒マスターにない学籍番号 | `STUDENT_NOT_FOUND` | 警告 |
| 対象クラスと違う学籍番号 | `STUDENT_CLASS_MISMATCH` | エラー |
| 必須の枠が`出場しない`、または未入力の`調整中` | `REQUIRED_SLOT_MISSING` | エラー |

`STUDENT_NOT_FOUND`を警告にしているのは、転入直後などで生徒マスターへ載っていない生徒が稀にいるためである。エラーにすると1人のためにクラス全体の申請が承認できず、名簿作成まで止まる。警告なので承認者が内容を見て判断でき、自動一括承認の対象からは外れる。警告のまま名簿を作ると、その枠の氏名は`（名簿未登録）`と印字される。生徒マスターへ追加してから再検査すれば正しい氏名に変わる。年度の方針として厳しくしたい場合は、`ルール設定`へ判定`エラー`の`INVALID_ID == 0`を追加する。

代理入力、同一クラスからの複数回答、受付停止中の修正申請、`調整中`、欠員許可の空き枠は、従来どおり常時の警告とする。これら以外の登録内容の判定は、すべて論理式ルールで行う。

### 既定で作成されるルール

初期作成時は次の行を書き込む。すべて論理式で書かれており、内容も判定も利用者が変更できる。上の常時チェックと重複する内容は入れない。

| rule_id | 有効 | 判定 | 論理式 | ねらい |
|---|---|---|---|---|
| R001 | ○ | エラー | `MAX_PER_EVENT <= 1` | 同じ競技へ同じ生徒を2回入れない |
| R002 | ○ | 警告 | `NAME_MISMATCH == 0` | 氏名欄があった頃の旧回答の表記違いを確認する |
| R003 | − | 警告 | `MAX_PER_STUDENT <= 2` | 競技をまたいだ出場数を1人2競技までにする |
| R004 | − | エラー | `F == 0 && UNKNOWN == 0` | 指定競技を男子のみにする |
| R005 | − | エラー | `M == 0 && UNKNOWN == 0` | 指定競技を女子のみにする |
| R006 | − | エラー | `M >= 2 && F >= 2` | 指定競技へ男女各2名以上入れる |

`INVALID_ID`、`CLASS_MISMATCH`、`REQUIRED_EMPTY`は常時チェックで枠ごとにエラーになるため、既定のルールには入れていない。申請全体でまとめて判定したい場合だけ、`INVALID_ID == 0`のような行を追加する。

| 変数 | 意味 |
|---|---|
| `M` | 対象競技に登録された男子人数 |
| `F` | 対象競技に登録された女子人数 |
| `N` | 対象競技の登録人数 |
| `UNKNOWN` | 性別不明または学籍番号を確認できない登録数 |
| `EMPTY` | `出場しない`の枠数 |
| `REQUIRED_EMPTY` | 必須だが登録済みでない枠数 |
| `UNIQUE` | 登録された学籍番号の種類数 |
| `DUPLICATE` | 同じ学籍番号の2件目以降の合計数 |
| `MAX_PER_STUDENT` | 対象競技全体での1人の最大登録数 |
| `MAX_PER_EVENT` | 1つの競技の中での1人の最大登録数（同一競技内の重複判定に使う） |
| `INVALID_ID` | 生徒マスターにない学籍番号の登録数 |
| `NAME_MISMATCH` | 生徒マスターと氏名が異なる登録数（氏名入力のある旧回答のみ対象。学籍番号だけの回答では常0） |
| `CLASS_MISMATCH` | 対象クラスと所属が異なる登録数 |
| `PENDING` | 調整中の枠数 |

使用できる演算子は`>=`、`<=`、`>`、`<`、`==`、`!=`、`+`、`-`、`*`、`/`、`%`、`&&`/`AND`、`||`/`OR`、`!`/`NOT`、括弧である。先頭の`=`は付けても付けなくてもよく、大文字・小文字は区別しない。例：男子のみは`F == 0 && UNKNOWN == 0`、女子のみは`M == 0 && UNKNOWN == 0`、男女各2名以上は`M >= 2 && F >= 2`、同一競技内の重複なしは`MAX_PER_EVENT <= 1`。

式は専用パーサーで評価し、JavaScript、セル関数、外部通信は実行しない。未知の変数、不正な記号、0除算、TRUE/FALSEにならない式は設定エラーとする。

`MALE`は`M`、`FEMALE`は`F`、`TOTAL`は`N`、`UNKNOWNS`は`UNKNOWN`として読み替える。全角の記号や数字はNFKCで半角へ正規化し、`TRUE`・`FALSE`をそのまま書くこともできる。式は500文字以内とする。

### 書き方の手順

1. 「こうなっていれば正しい」状態を日本語で決める。例：「男女を各2人以上入れる」。
2. 数える対象を上の変数へ置き換える。例：男子人数は`M`、女子人数は`F`。
3. `>=`などの比べる記号でつなぐ。例：`M >= 2 && F >= 2`。
4. 対象競技は式へ書かず、`ルール設定`右側の`対象競技:`チェック欄で選ぶ。
5. `判定`列でエラー（承認不可）か警告（確認後に承認可）を決め、`表示メッセージ`へ利用者向けの文を書く。
6. `設定を点検`を実行し、式の誤りが行番号付きで出ないことを確認する。

### よく使う式

| やりたいこと | 論理式 |
|---|---|
| 男子だけで登録する | `F == 0 && UNKNOWN == 0` |
| 女子だけで登録する | `M == 0 && UNKNOWN == 0` |
| 男女を各2人以上入れる | `M >= 2 && F >= 2` |
| 同じ競技へ同じ生徒を2回入れない | `MAX_PER_EVENT <= 1` |
| 競技をまたぐ出場を2競技までにする | `MAX_PER_STUDENT <= 2` |
| 必要な枠を全部埋める | `REQUIRED_EMPTY == 0` |
| 名簿にない学籍番号を入れない | `INVALID_ID == 0` |
| 4人のうち3人以上を女子にする | `F >= 3` |
| 男子だけ、または女子だけにする | `M == 0 || F == 0` |

### よくある誤り

| 書き方 | 結果 | 直し方 |
|---|---|---|
| `M = 2` | エラー | 等しいは`==`と二つ重ねる。 |
| `M + F` | エラー（TRUE/FALSEにならない） | `M + F >= 4`のように比べる記号を入れる。 |
| `BOYS >= 2` | エラー（未知の変数） | 使える変数は上の表のとおり。男子は`M`。 |
| `IF(M>=2, TRUE, FALSE)` | エラー | セル関数は使えない。`M >= 2`と書く。 |
| `2 <= M <= 4` | エラー | `M >= 2 && M <= 4`と分けて書く。 |
| `M >= 2 && F >= 2` を全競技へ適用 | 意図しないエラー | 対象競技のチェック欄で適用する競技だけを選ぶ。 |

利用者が入力するシートには同じ内容を短くまとめて置く。見出しメモは`設定を点検`のたびに最新の内容へ更新する。`ルール設定`の`論理式（TRUEなら問題なし）`列の見出しメモに、例・変数・記号・つまずきやすい点を表示し、`設定画面`サイドバーの手順1へ「論理式の書き方を見る」を置く。

## 操作手順

### 初回だけ行う高速作成の準備

Google Forms APIはApps Scriptの「サービス」追加ではなく、Apps ScriptからGoogle公式REST APIを呼び出して使用する。初回だけ次を行う。

1. Google Cloudで本システム専用の標準プロジェクトを作成または選択する。
2. `APIとサービス` → `ライブラリ`で`Google Forms API`を有効にする。
3. Apps Scriptエディタの`プロジェクトの設定`で、上記Google Cloudプロジェクトのプロジェクト番号へ切り替える。
4. スプレッドシートを再読み込みし、フォーム下書き作成を実行して追加権限を承認する。

この準備を行わない運用も選べる。設定画面の`Google Forms APIを使わずに作る`を押すと、Apps Script標準の`FormApp`だけでフォームを作成する。Google CloudでのAPI有効化は不要で、できあがるフォームの内容・質問の並び・`フォーム項目対応表`は高速作成と同じになる。質問を1つずつ作るため完成までの時間は長くなる。

`Google Forms APIを利用できません`と表示された場合は、上記2と3を確認した後、設定画面の`中断した場所から再開する`を押す。API有効化を行わない場合は`途中の作成を取り消す`を押してから、`Google Forms APIを使わずに作る`で作り直す。既に旧方式で作成中だったジョブを高速方式へ途中変換はしない。高速方式を使う場合は`途中の作成を取り消す`を押して、新しく下書きを作り直す。

1. 初回だけ`選手登録管理`メニューの`フォーム・競技設定`から`設定シートを作成・不足分を補う`を実行する。
2. 同じメニューから設定シートを開く。
   - ルール設定では、右側の緑色の競技列にチェックを入れて対象を複数選ぶ。
3. `設定を点検`を実行する。
4. `設定点検結果`のエラーを0件にする。
5. `フォーム下書きを作成`を実行する。
6. 表示された2つの編集URLから内容を確認する。

下書きは公開しない。公開確定時に項目対応表と実フォームの設問ID・表示名・形式を比較し、差分が1件でもあれば公開しない。全学年の競技は学年ページごとに同じ`field_key`が作られるため、想定件数（全学年の競技は3件、それ以外は1件）以内の重複は差分としない。公開中の設定シートを直接編集した場合は、編集したシートだけを公開時スナップショットへ自動復元する。`競技設定`・`フォーム設計`の変更は`受付を停止して設定変更を開始`から理由を入力し、下書き再作成・確認・公開を行う。前年度コピーは未実装。

### ルール設定だけの変更

`ルール設定`はフォームの設問構成に影響しない。判定に使うのは申請を検査する時点の`ルール設定`だけで、フォーム生成では読み込まない。そのため、フォーム受付を続けたまま、フォームを作り直さずに変更できる。

1. `選手登録管理` → `フォーム・競技設定` → `ルール設定だけを変更する`で理由を入力する。`ルール設定`だけが編集可能になり、`競技設定`と`フォーム設計`は保護したままとする。フォームの受付状態と公開URLは変えない。
2. `ルール設定を開く`から論理式・判定・対象競技を直す。
3. `ルール変更を確定して全申請を再検査`を実行する。設定点検でルールのエラーが0件のときだけ確定し、確定後に受信済みの全申請を新しいルールで検査し直す。
4. 途中でやめる場合は`ルール変更を取り消す`で、変更を始めた時点の`ルール設定`へ戻す。

再検査では`承認済み`・`名簿反映済み`・`却下済み`・`保留`の申請の状態を変えず、警告・エラーの件数だけを更新する。新しいルールで承認済み・名簿反映済みの申請がエラーになった場合は件数を表示し、担当者が`承認を取り消して確認待ちに戻す`で対応する。エラーが残っている間は`承認済みから選手名簿を作成`が止まる。

ルールの確定は再検査より先に行うため、申請件数が多く再検査が実行時間上限で止まった場合でも、変更したルールは確定済みとなる。その場合は`すべて再検査する`をもう一度実行すればよい。

開始・確定・取消はそれぞれ理由付きで`設定変更履歴`へ記録する。ルール設定の変更中は`フォーム下書きを作成`と`受付を停止して設定変更を開始`を実行できない。

フォームが公開されていない状態でも同じ操作を使える。この場合は設定シートの保護状態を変えずに、理由の記録・点検・全申請の再検査だけを行う。

### 設定シートの保護状態

設定シートの保護は、フォーム状態が`公開中`または`公開前確認`のときだけ有効とする。公開後に`未作成`や`受付停止`へ戻ったのに保護フラグだけが残っていた場合、設定シートを解除する手段がなくなるため、保護状態を確認した時点でフラグを解除して編集できる状態へ戻す。現在の状態は`設定画面`の`設定の保護`行に表示し、`そのまま編集できます`・`保護中です`・`ルール設定だけ編集できます（変更中）`・`設定変更中です`のいずれかを示す。

公開中のフォームがない状態で`受付を停止して設定変更を開始`を実行した場合は、現在のフォーム状態と、設定シートをそのまま編集してよいこと、ルールだけならルール専用操作が使えることをエラーメッセージへ示す。

### 「設定シートを作成・不足分を補う」の説明表示

実行前に、次の内容を画面へ表示して確認を求める。

- フォーム準備に必要な設定シート、見出し、選択欄を作る。
- 空の設定シートだけに疑似の見本設定を入れる。
- 入力済みの設定行は消さない。
- Googleフォーム、申請、登録データ、帳票は変更しない。

設定サイドバーで設定シートが不足している場合も、同じ内容をボタンの直前に常時表示する。

## 設定サイドバー

`設定画面を開く`と、現在の状態から次に必要な操作を1つだけ強調したサイドバーを表示する。

- 設定シートがない場合：`設定シートを準備する`
- エラーがある場合：`最初のエラー箇所を開く`
- 警告だけの場合：`最初の警告箇所を開く`
- 問題がない場合：`2つのフォーム下書きを作る`、または`Google Forms APIを使わずに作る`
- 作成完了後：`通常フォームの下書きを開く`、`確認済みの2フォームを公開する`

作成完了後は`公開前確認`とし、新フォームには回答送信トリガーを付けず、現在使用中のフォームも停止しない。確認後に明示的な公開操作を行い、新フォームの公開・回答受付・トリガー設定が成功してから旧フォームを停止してGoogle Driveのゴミ箱へ移動する。公開前フォームを破棄した場合は現在使用中のフォームへ戻す。

フォーム作成はApps Scriptの実行時間上限を避けるため、通常フォームの基本項目、学年ページ、競技項目、修正フォームの基本項目、競技項目、最終切替に分割する。作成方式は開始時のボタンで決まり、途中で切り替えない。`2つのフォーム下書きを作る`はGoogle Forms API方式、`Google Forms APIを使わずに作る`は`FormApp`方式で、分割の単位・進捗表示・再開・取り消しはどちらも同じ仕組みを使う。Google Forms API方式では`batchUpdate`を使い、1競技分の設問を1回の通信で一括追加する。Forms APIで設定できない学籍番号4桁の回答検証とセクション終了後の送信動作だけを最終段階で`FormApp`から設定する。APIへ送るのは設問定義と競技設定だけで、生徒マスター・回答・氏名・学籍番号の入力値は送らない。既に開始済みの旧方式ジョブは保存済み進捗との互換性のため`FormApp`方式で再開する。1回の実行では最大8区切りをまとめて処理し、各区切りの完了直後に進捗を保存する。8区切り未満でも処理開始から約2分に達した場合は終了し、次回へ引き継ぐ。設定画面を開いている間は約5秒ごとに次の一括処理を実行し、閉じた後は時間主導トリガーで継続する。作成中の進捗取得ではルール設定同期・生徒マスター読込・全設定再点検を省略し、ジョブ開始時に保存した件数と競技設定だけを使う。設定画面には全区切り数に対する完了数と百分率のプログレスバー、現在作成中のフォーム・学年・競技数・最終更新時刻を表示する。途中で例外が発生した場合は中断地点を保存し、`中断した場所から再開する`または`途中の作成を取り消す`を選べる。取り消し時は作成途中の新フォームだけをゴミ箱へ移し、現在使用中のフォームと設定は変更しない。

作成開始後に競技設定またはフォーム設計が変更された場合は、異なる設定が1つのフォームへ混在しないよう中断する。利用者は途中の作成を取り消し、現在の設定から改めて作成する。

`フォーム項目対応表`は処理済み回答の追跡用に過去フォーム分もフォームIDごとに保持するが、古いフォームから新しい回答は受け付けない。設定サイドバーから保存先の`forms`フォルダを開ける。

画面内に設定→点検→下書き確認→公開の進行状況、競技・有効ルール・警告・エラー件数、最大5件の修正カードを表示する。カードの`この場所を開く`で元の設定シートと行へ移動する。設定シートの列見出しには入力内容の説明を注記する。
