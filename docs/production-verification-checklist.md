## 2. 生徒マスター

- [ ] A列の4桁学籍番号、B列の氏名、F列の性別`m`/`f`を読み込める。
- [ ] C～E列の学年・組・出席番号が学籍番号から正しく自動表示される。
- [ ] `m`、`f`、`M`、`F`、全角`ｍ`/`ｆ`がM/Fへ正規化される。
- [ ] 性別の空欄およびm/f以外を、該当行付きのエラーとして拒否する。
- [ ] `神　山　瑠　星`のような半角・全角・タブ・改行・ゼロ幅空白入り氏名を、空白なしの入力と同一判定する。
- [ ] 存在しない学籍番号、別クラスの学籍番号、重複番号、氏名表記差（氏名欄があった頃の旧回答が対象）を仕様どおり判定する。
- [ ] 1～3年・1～8組、39人・40人・41人、欠番、同姓同名を処理できる。
- [ ] 本番用生徒マスターが1行でもある場合、疑似生徒マスターへ黙って戻らない。

## 3. ルール設定と論理式

- [ ] `ルール設定`の右側で、対象競技を複数チェックできる。
- [ ] 既存の対象競技チェックが論理式列追加後も保持されている。
- [ ] `F == 0 && UNKNOWN == 0`で男子のみを判定できる。
- [ ] `M == 0 && UNKNOWN == 0`で女子のみを判定できる。
- [ ] `M >= 2 && F >= 2`で男女各2名以上を判定できる。
- [ ] `N == 4`、`REQUIRED_EMPTY == 0`、`MAX_PER_EVENT <= 1`など性別以外の変数も判定できる。
- [ ] 式がTRUEのとき、ルール由来の問題を追加しない。
- [ ] 式がFALSEのとき、`判定`列に従いエラーまたは警告を申請全体へ1件だけ表示する。
- [ ] 修正フォームで1競技だけ送信した場合、申請に含まれない競技の式を誤判定しない。
- [ ] 未知の変数、不正記号、0除算、数値だけでTRUE/FALSEにならない式を設定エラーにする。
- [ ] 論理式へJavaScriptやスプレッドシート関数を書いても実行されない。
- [ ] `設定を点検`でエラーのシート、行、直し方が表示される。
- [ ] 論理式が空欄のまま`有効`にチェックがある行は、`設定を点検`で「論理式が空欄です」というエラーになる。
- [ ] 非表示の`旧条件（互換）`・`旧上限（互換）`列に何を書いても（従来のキーワードを書いても、削除しても）判定結果が変わらないことを確認する。
- [ ] 既定ルールR001（`MAX_PER_EVENT <= 1`、有効、エラー）を無効にすると、同じ競技内の重複登録がエラー・警告どちらにもならないことを確認する。
- [ ] `MAX_PER_EVENT`は同じ競技内の重複だけを数え、別の競技への出場は数えないことを確認する。競技をまたぐ出場数の上限は`MAX_PER_STUDENT <= 2`のルールで確認する。
- [ ] 既定ルールR002（`NAME_MISMATCH == 0`、有効、警告）を無効にすると、氏名表記差異の警告が表示されなくなることを確認する。

## 4. フォーム作成・公開・回答取込

- [ ] 通常登録フォームと修正フォームの下書きを作成できる。
- [ ] 各競技の選手枠の質問が学籍番号（欠員許可時は登録状態も）だけであり、氏名入力欄（`_slot??_name`）が生成されない。
- [ ] フォーム説明と各競技の説明に「学籍番号だけを入力し、氏名は名簿から自動照合する」旨の案内が表示される。
- [ ] 作成中断後に途中から再開でき、取り消しても現行フォームを変更しない。
- [ ] 公開直前に設問ID、設問名、形式、未登録項目を点検する。
- [ ] テストフォームの設問名または形式を手動変更すると、公開を拒否する。
- [ ] 公開成功後だけ新フォームの回答受付と送信トリガーが有効になる。
- [ ] 新フォームの公開に失敗した場合、現行の本番フォームが受付可能なまま残る。
- [ ] 通常回答と修正回答が`フォーム回答原本`へ保存され、承認待ち申請へ変換される。
- [ ] フォーム送信だけでは`登録データ`と帳票が変わらない。
- [ ] 回答取込のたびに全申請・全表を書き換えず、追加・影響対象だけを処理する。
- [ ] 同時送信、同じ回答の再処理、取込途中の例外で重複申請を作らない。

## 4.5 実機テスト（本物のフォームでの確認）

> 対象クラスは、まだ申請のないクラスを選びます。テストの申請は本物の`承認待ち`へ入るため、確認後に必ず片付けます。

- [ ] `1. テストを準備する`で対象クラスを指定でき、`実機テスト`シートに事前入力URLが並ぶ。
- [ ] 事前入力URLをフォーム画面で送信すると、`3. 結果を照合する`で`OK`になる。
- [ ] `2. テストを自動送信する`で全件が送信され、`取込経路`列に`トリガー`または`再処理`が記録される。
- [ ] 在籍しない学籍番号のテストで`STUDENT_NOT_FOUND`が警告として、別クラスの学籍番号のテストで`STUDENT_CLASS_MISMATCH`がエラーとして実際に出る。
- [ ] 判定が`NG`のとき、`差分`列に不足・想定外の判定コードが表示される。
- [ ] テストの申請が`承認待ち`で入力者`9999`・`実機テスト（削除予定）`として見分けられる。
- [ ] `4. テストの申請を片付ける`で、テストの申請・フォーム回答原本・検査結果が消え、本物の申請と生徒マスターが残る。
- [ ] 片付け後、同じクラスの本物の申請の警告件数が、テスト送信前と同じに戻っている。
- [ ] 承認済みのテスト申請があるときは片付けを中止し、取り消しを促す。
- [ ] 前回のテストが残っている状態で`1. テストを準備する`を実行すると、先に片付けるよう促す。

## 5. 承認・修正・ロールバック

- [ ] 問題なし、警告あり、エラーありの表示件数が実データと一致する。
- [ ] エラー申請を承認できない。
- [ ] 承認画面の各選手枠に「名簿の氏名」（生徒マスターから引いた氏名）が表示される。名簿に無い学籍番号は「名簿で確認できません」と表示される。
- [ ] 論理式ルールが満たされない申請では、そのルールの判定に使った競技の登録内容が一覧表示され、各行から「この項目を修正」を開ける。
- [ ] 警告申請は確認理由を残して承認できる。
- [ ] 保留、修正依頼、却下、却下取消を理由付きで操作できる。
- [ ] 同一クラスの複数初回回答から採用する1件を選べる。
- [ ] 修正フォームの変更理由と対象競技を確認できる。
- [ ] 承認操作だけでは正式名簿を更新せず、名簿作成完了時だけ反映する。
- [ ] 承認処理・名簿最終反映中の意図的な例外で途中反映を残さず、再実行または復元できる。
- [ ] 承認者、理由、変更前後、日時が履歴へ残る。

## 6. 名簿・差分強調・PDF

- [ ] 種目別、クラス別・招集順、当日変更用の3スプレッドシートを生成できる。
- [ ] クラス配布用PDFを同じ版フォルダへ自動生成できる。
- [ ] PDFが1ページ1クラスで、各クラスの全登録を含む。
- [ ] 39人・40人・41人のクラスや登録数が多いクラスでも、文字切れ・重なり・欠落がない。
- [ ] PDFの学年、組、氏名、学籍番号、競技名、走順・役割、版名、作成日時が正しい。
- [ ] 修正フォームから承認・反映された選手枠だけが黄色で強調される。
- [ ] 初回回答由来の枠を誤って黄色にしない。
- [ ] 名簿作成中に停止して再開でき、取り消すと途中フォルダだけをゴミ箱へ移す。
- [ ] 4ファイルがすべて完成するまで正式`登録データ`と申請状態を変更しない。
- [ ] 同じ名前で再作成すると新しい版番号になり、旧版を上書きしない。
- [ ] 配布前にPDF全ページを人が目視確認した。

## 7. 公開後の設定変更

- [ ] 公開中に`競技設定`、`ルール設定`、`フォーム設計`を直接編集すると公開時の値へ戻る。
- [ ] `受付を停止して設定変更を開始`では変更理由が必須になる。
- [ ] 設定変更開始時に通常フォームと修正フォームの受付が停止する。
- [ ] 変更後の下書き作成・確認・公開を完了すると、新設定で受付を再開する。
- [ ] 公開前フォームを破棄すると設定変更を取り消し、元のフォーム受付を再開する。
- [ ] 設定変更開始、反映、取消、公開中の直接編集取消が`設定変更履歴`へ残る。

## 8. 本番・練習データの分離

- [ ] `本番モードへ切り替える`の確認画面に、削除するものと残すものが件数付きで表示される。
- [ ] 確認欄に`本番開始`以外を入力すると、何も削除せず中止する。
- [ ] 切替後、`承認待ち`、`申請項目`、`検査結果`、`承認履歴`、`変更履歴`、`フォーム回答原本`、`登録データ`、`疑似生徒マスター`、`実機テスト`、`選手名簿作成履歴`がヘッダー行だけになる。
- [ ] 切替後に`回答取込を点検・再処理`を実行しても、開発中のテスト回答が取り込まれない。
- [ ] 切替後に表示された選手名簿フォルダのURLを開き、不要な開発中の名簿を手動で削除した。
- [ ] 切替後、`競技設定`、`ルール設定`、`フォーム設計`、`フォーム項目対応表`、本番用`生徒マスター`、Googleフォーム本体が残っている。
- [ ] 本番モードでは本番ファイル上の疑似データ作成・削除操作が無効になる。
- [ ] 本番モードの`選手登録管理`メニューに`開発用モードへ戻す`が表示され、理由を入力すると開発用モードへ戻る。
- [ ] 開発用モードへ戻した後、スプレッドシートを再読み込みすると開発用メニューへ戻り、申請・登録データ・履歴が消えていない。
- [ ] 開発用モードへ戻した後も、本番用`生徒マスター`に入力がある間は疑似データ機能が無効のままである。
- [ ] 本番切替と開発用モードへの復帰が`設定変更履歴`へ実行者・日時・理由付きで残る。
- [ ] 本番ファイルから個人情報を除去した`練習用コピー`を作成できる。
- [ ] 練習用コピーに本番フォームID、実回答、登録データ、履歴、生徒マスターが残らない。
- [ ] 練習用コピーでは、そのコピー内で作成したフォームだけを公開・停止・破棄できる。
- [ ] 練習用コピーから本番フォームを停止・削除しようとしても拒否する。
- [ ] 本番フォームと本番管理ファイルが練習操作後も受付可能・変更なしである。

## 9. 最終Go/No-Go

以下がすべて満たされた場合だけ本番運用を開始します。

- [ ] 上記の必須項目に未解決の`NG`がない。
- [ ] 実在データを使わない一連の通し試験が完了した。
- [ ] 第三者が[操作マニュアル](operation-manual.md)だけで主要操作を完了した。
- [ ] 本番生徒マスターの人数、重複、欠番、性別m/f、所属を担当者が照合した。
- [ ] 本番フォームURLを配布する前に、フォームタイトル、年度、締切、対象競技、受付状態を確認した。
- [ ] 初回配布用PDFを全ページ確認する担当者と、旧版を配布しない保管ルールが決まっている。
