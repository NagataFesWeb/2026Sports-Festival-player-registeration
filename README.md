# 体育祭 選手登録・名簿管理システム

> Googleフォームの回答を安全に確認・承認し、用途別の選手名簿へ反映する体育祭運営システム。

各クラス代表者がGoogleフォームから選手登録または修正申請を行い、体育祭スタッフ招集パートが内容を確認・承認した場合にのみ正式名簿へ反映します。フォーム送信だけでは名簿を書き換えません。PC操作に不慣れな担当者でも扱えるよう、管理画面では「警告○件」「エラー○件」を押して詳細確認・修正・承認・保留・却下を行えるUIを提供します。

過去運用では、フォーム回答から名簿への手作業転記、入力揺れ、訂正対応が名簿完成の遅延要因となっていました。また、Google Forms化を試みたものの訂正多発で紙運用へ戻った年度もありました。本システムは、登録・検査・承認・反映を分離して再発を防ぎます。

## 主な機能

- **通常登録フォーム** — 学年別に分岐し、競技設定から入力欄を自動生成
- **修正申請フォーム** — 変更前後と理由を記録し、承認後のみ反映
- **警告・エラー管理** — 件数表示から詳細一覧を開き、修正・承認・却下が可能
- **生徒マスター照合** — 学籍番号を主キーとして実在確認。選手枠は学籍番号のみを入力し、氏名は生徒マスターから照合して表示（氏名欄があった頃の旧回答の氏名表記差は警告扱い）。`m`/`f`の性別をルール判定に利用し、申請確認画面の各選手枠へ`男（M）`・`女（F）`・`UNKNOWN`として表示
- **論理式ルール** — `M >= 2 && F >= 2`のような式がTRUEなら通過、FALSEならエラーまたは警告
- **承認ワークフロー** — フォーム送信では名簿を変更せず、招集パートの承認後に反映
- **却下の取り消し** — 却下済み一覧から理由付きで確認待ちへ戻し、現在の内容を自動再検査
- **用途別帳票** — 種目別、クラス別・招集順の統合版、当日変更用に加え、1ページ1クラスの配布用PDFを生成
- **変更履歴** — 申請者、承認者、変更前後、理由、日時、影響帳票を保存
- **機能紹介** — メニューの「この管理表でできること」で、全機能を分類ごとに一覧。何をする／作るもの／変えないもの／いつ使うか／今使えるかを表示。使えない機能には「先に◯◯をしてください」を添える
- **疑似データ開発** — 実在の個人情報をLLMや開発環境へ渡さずに開発可能。生徒マスターに実在の生徒を入力したあとでも、開発用モードなら疑似データを作れる。疑似申請の選手を「疑似生徒マスター」と「生徒マスター」のどちらから選ぶかは「疑似データ設定」シートで切り替える（既定は疑似生徒マスター。2つの名簿を混ぜることはない）
- **全校規模の負荷確認** — 疑似生徒数と同じ件数の疑似申請を初期値とし、申請・エラー・警告件数を設定可能
- **未出場点検** — 出場登録がない生徒の人数を、申請ごとに重複させず全体警告1件で表示

詳細な受け入れ条件は [docs/spec.md](docs/spec.md) を参照してください。

機能の一覧をこのREADMEに全部書くことはしません。正本は `src/core/feature-catalog.ts` で、スプレッドシートのメニュー「選手登録管理」→「この管理表でできること」から、いま使える状態も含めて読めます。カタログに登録し忘れた機能があると `npm test` が落ちるので、一覧が実装より古くなることはありません。

## 現在の実装範囲

claspで配備できる初期実装として、次を実装済みです。

- 1〜3年・1〜8組、39〜41人、欠番を含む疑似生徒マスター生成
- 問題なし・警告・エラー・受付停止を含む疑似フォーム回答生成
- 学籍番号・氏名の正規化、生徒存在・所属・重複等の自動検査
- `操作画面`と`承認待ち`シート、警告・エラー等の件数表示
- サイドバーの申請一覧、問題詳細、承認・保留・却下
- サイドバーからの申請項目修正、理由付きの変更履歴、自動再検査
- 操作権限確認、排他制御、承認履歴
- 承認済み申請から`登録データ`を作成し、3種類の選手名簿を独立ファイルで出力
- 名簿作成前のバックアップ、失敗時の復旧、版名と作成履歴の保存

承認操作では申請状態を`APPROVED`にして承認履歴へ記録します。この時点では`登録データ`と名簿は変わりません。メニューの`承認済みから選手名簿を作成`を実行すると、時間切れを避けるため3種類のスプレッドシートとクラス配布用PDFを1ファイルずつ自動作成します。全ファイルが完成するまで正式な`登録データ`と申請状態は変更せず、最後の処理でだけ`登録データ`へ反映して申請を`APPLIED`にします。

名簿作成時は毎回、名簿の名前を入力します。初回は`入力名_v1.0`、同じ入力名が既にあれば`v1.1`、`v1.2`と空いている番号へ自動で進みます。管理スプレッドシートと同じ場所に`選手名簿`フォルダを作り、その中の版フォルダへ3種類のスプレッドシートとクラス配布用PDFを順番に保存します。`名簿作成状況`シートとメニューから進捗を確認でき、停止時は同じファイルから再開できます。取り消した場合は途中フォルダをゴミ箱へ移し、正式データは変更しません。

3つの名簿はすべて配布・PDF化を前提とします。種目別名簿は`競技設定`の`表示順`を100で割った商でシート（ページ）を分けます。表示順0・100・200はそれぞれ別のシート、300・301・302は1枚のシートにまとまります。学年ごとに競技を細かく分けている場合に1枚へまとめて印刷できるようにするための区切りです。各シート内へ1年、2年、3年の`走順×クラス`表を上から並べます。統合版は`クラス別 1年`〜`クラス別 3年`と`招集順 1年`〜`招集順 3年`を1ファイルへ収録します。走順別ファイルは作成しません。当日変更用は種目別と同じ競技別シート・`走順×クラス`表とし、各選手欄に変更記入欄を付けます。競技設定にある全競技・全枠を必ず表示し、まだ選手がいない場所は空欄として残します。各ファイルの先頭シート`自分の競技を探す`では、同じ選手の出場競技と走順を1行にまとめ、追跡用IDは非表示の`_管理用データ`シートへ保存します。すべての名簿とクラス配布用PDFには、名簿作成時点の生徒マスターから引いた性別を`男`・`女`・`UNKNOWN`で表示します。修正フォームから承認・反映された選手枠は黄色で強調します。

フォーム保守機能として、`競技設定`・`フォーム設計`・`ルール設定`の作成と点検、通常登録フォーム・修正申請フォームの非公開下書き生成、`field_key`を持つ`フォーム項目対応表`の保存、公開確定前のフォーム構造差分検査、公開後設定の編集防止と理由付き変更履歴に対応しています。年度コピーは未実装です。

`ルール設定`はフォームの設問構成に影響しないため、フォーム公開後でも受付を止めず、フォームを作り直さずに変更できます。`選手登録管理` → `フォーム・競技設定` → `ルール設定だけを変更する`で理由を入力し、式を直したら`ルール変更を確定して全申請を再検査`を実行します。確定時にルールのエラーが0件であることを点検し、受信済みの申請をすべて新しいルールで検査し直します。承認済み・名簿反映済みの申請は状態を変えず、警告・エラーの件数だけを更新します。新しいルールでエラーになった承認済み申請は件数を表示し、`承認を取り消して確認待ちに戻す`で直すまで選手名簿を作成できません。編集をやめる場合は`ルール変更を取り消す`で元の内容へ戻ります。

生成フォームは管理スプレッドシートと同じ場所の`forms`フォルダへ保存します。フォーム回答は送信トリガーで`フォーム回答原本`へ保存した後、承認待ち申請へ変換して自動検査します。回答送信だけでは正式データや帳票を変更しません。

## ローカル開発

```bash
npm install
npm run lint
npm run typecheck
npm test
npm run build
```

`dist/`にclaspへ送るGASファイルが生成されます。実在データを含まないテスト用のスプレッドシートと、テスト専用Apps Scriptプロジェクトを用意してください。

入口関数ごとの実行時間は、Apps Scriptエディタの「実行数」で各実行のログに`[実行時間] 関数名 1234ms`として残ります。関数名とミリ秒だけを記録し、引数や氏名・学籍番号は記録しません。速さを比べるときは、練習用コピーで同じ操作を前後で行い、この値を見比べてください。

```powershell
Copy-Item .clasp.json.example .clasp.json
# .clasp.json の scriptId をテスト用Apps ScriptプロジェクトのIDへ変更
npm run clasp:push
```

スプレッドシートを再読み込み後、次の順に実行します。

1. `選手登録管理` → `フォーム・競技設定` → `設定シートを作成・不足分を補う`
2. 設定画面で点検し、通常フォームと修正フォームの下書きを作成
3. `選手登録管理` → `開発用の疑似データを作る`

フォーム下書きは競技単位に分割してバックグラウンド作成します。設定画面を閉じても続行し、再度開くと進み具合を確認できます。途中で停止した場合は、設定画面の`中断した場所から再開する`または`途中の作成を取り消す`を使用してください。2つの新フォームが完成するまで、現在使用中のフォームは変更されません。

高速作成には、Apps Scriptへ関連付けた標準Google Cloudプロジェクトで`Google Forms API`を有効にする必要があります。初回の設定方法は[docs/settings.md](docs/settings.md)の「初回だけ行う高速作成の準備」を参照してください。以前から作成中のジョブは安全のため旧方式のまま再開します。高速方式で作り直す場合は、途中の作成を取り消してから新しく下書き作成を開始してください。

`フォーム設計`の締切はセルのカレンダーから選びます。日本標準時の日付として扱い、曜日を自動計算して`2026/09/13(日)`の形式でシートとフォーム説明へ表示します。時刻と曜日の手入力は不要です。

疑似回答・疑似申請は、手順2で作ったフォームの競技、選手枠、走順、必須・任意の構成から生成されます。フォーム下書きがない場合は疑似データを作成しません。

疑似申請の選手は、`ルール設定`の`有効=TRUE`のルールをすべて読んで割り当てます。「この競技は女子のみ」「騎馬は同性で構成」「大縄跳びは前半・後半どちらか一方だけ」のような論理式は、問題なしの疑似申請では満たされます。エラーを含む申請数・警告を含む申請数に指定した件数だけは、逆に`判定=エラー`／`判定=警告`のルールを1つずつ順番に破って作ります。狙った重さのルールが無い場合は、学籍番号の書式違反・別クラスの学籍番号・代理入力で代用します。

ルール同士が矛盾しているなど、どうしても満たせないルールがある場合でも疑似申請は作成します。作成後のダイアログに、どのクラスのどの競技でどのルール（`rule_id｜ルール名`と論理式）が満たせなかったかと、意図的な問題をどう作ったかを表示します。1つの競技で欠員を許可していない登録枠がクラスの人数を超えている場合だけは、同じ競技へ同じ生徒を登録できないため作成を中止します。

初回は1〜3年・1〜8組の全校を対象とします。`選手登録管理` → `疑似データの対象範囲を設定`では、学年、クラス、通常フォーム、修正フォームをチェックボックスで選べます。通常フォームは選択した各クラスにつき1回答だけ作ります。両方を選んだ場合は各クラスの最初の1回答だけを通常フォームとし、残りを修正フォームとして、対象範囲の疑似生徒数と同じ件数まで作ります。修正フォームだけの場合も対象範囲の疑似生徒数と同じ件数を作ります。エラーを含む申請数と警告を含む申請数も変更できます。

登録のない生徒がいる場合は、人数にかかわらず`出場していない生徒がN人います`という全体警告1件だけを表示します。警告内の一覧で、該当する生徒のクラス・学籍番号・氏名を確認できます。通常運用は正式な`登録データ`、疑似データの確認中は現在の疑似`申請項目`を基準に数えます。

動作確認を終えたら、`選手登録管理` → `開発用の疑似データをすべて削除`を実行できます。疑似生徒・疑似フォーム回答・疑似申請と、それらに対応する検査結果・承認履歴・変更履歴だけを削除します。作成済みフォーム、設定、フォーム項目対応表、登録データ、帳票は残します。

本番用へ切り替えるときは、`選手登録管理` → `本番用の生徒マスターを開く`を選び、黄色のA列へ4桁学籍番号、B列へ氏名、F列へ性別`m`または`f`を入力します。学年・組・出席番号は自動表示されます。1件でも入力すると本番用`生徒マスター`が優先され、全行空欄の場合だけ`疑似生徒マスター`を使用します。入力不足、重複、m/f以外の性別がある場合は行番号付きで処理を止めます。実在データはスプレッドシート外へコピーしないでください。

`ルール設定`の`論理式（TRUEなら問題なし）`には、男子のみなら`F == 0 && UNKNOWN == 0`、女子のみなら`M == 0 && UNKNOWN == 0`、男女各2名以上なら`M >= 2 && F >= 2`と入力します。任意のJavaScriptやスプレッドシート関数は実行せず、許可された変数と演算子だけを安全に評価します。

論理式の全変数・演算子・設定例は[ルール論理式の完全ガイド](docs/rule-expression-guide.md)を参照してください。

時間差で修正フォームが届く状況を試す場合は、申請一覧下部または`選手登録管理`メニューの`疑似の修正申請を追加する`を使います。既存の疑似申請と履歴を残したまま、指定件数の問題なし修正申請を追加します。

承認済み・名簿反映済み申請は、詳細画面の`承認を取り消して確認待ちに戻す`から理由付きで戻せます。名簿反映済みの場合は、残っている反映済み申請から`登録データ`を再構築します。過去のPDFは監査用の旧版として残るため、修正・再承認後に新しい名簿版を作成してください。名簿作成中は実行できません。

本番用生徒マスターを入力した後、`選手登録管理` → `本番モードへ切り替える`を実行します。切替では、開発中に作った承認待ち・申請項目・検査結果・承認履歴・変更履歴・フォーム回答原本・登録データ・疑似生徒マスター・疑似データ設定・実機テスト・選手名簿作成履歴と、Googleフォームに届いているテスト回答をすべて削除します。削除するものと残すものを件数付きで表示し、確認欄へ`本番開始`と入力した場合だけ実行します。設定、フォーム項目対応表、本番用生徒マスター、Googleフォーム本体は残ります。開発中に作った選手名簿のDriveフォルダは自動削除せず、切替後にURLを表示するので手動で削除します。本番モードから開発用モードへ戻す場合は、`選手登録管理` → `開発用モードへ戻す`に理由を入力します。運用モードだけを戻し、申請・登録データ・履歴は削除しません。本番用生徒マスターに入力がある限り、開発用モードへ戻しても疑似データ機能は無効のままです。体育祭スタッフ専用の共有Gmailアカウントでこの操作を行い、その1アカウントを担当者として登録します。管理スプレッドシート、Apps Script、生成フォーム、時間主導トリガーは同じ共有Gmailアカウントで所有・実行します。アカウントの復旧先、2段階認証、保管担当を校内で記録してください。本番モードでも、個人情報を除去した別ファイルの`練習用コピー`は作成できます。本番フォームは練習用コピーから停止・削除できません。

本番開始後に疑似データで練習するときは、本番ファイルの`選手登録管理` → `練習用コピーを作成`を使用します。専用フォルダ内に練習用スプレッドシートを作り、本番フォームID、実回答、登録データ、履歴、生徒マスターをコピー側から切り離します。練習用コピーで作成したフォームだけを公開・停止・削除でき、本番フォームや本番ファイルは変更できません。練習用コピーを本番モードへ切り替えることもできません。

選手枠のフォーム入力は学籍番号のみで、氏名入力欄はありません。氏名は学籍番号から生徒マスターを照合して表示・記録します。氏名欄があった頃の旧回答や手入力の氏名と生徒マスターの氏名は、NFKC正規化後に半角・全角・改行・タブ・ゼロ幅空白をすべて除いて照合します。`神　山　瑠　星`と`神山瑠星`は同じ氏名として扱います。

通常のフォーム取込とサイドバーからの修正では、対象申請と同じクラスの重複候補だけを再検査します。全申請の再検査はメニューの`すべて再検査する`を明示的に実行した場合だけ行います。フォーム回答が申請一覧へ現れない場合は`回答取込を点検・再処理`で未取込・失敗回答を再処理できます。

名簿作成が完了すると、同じ版フォルダへ`クラス配布用選手名簿.pdf`を自動保存します。各クラスを必ず1ページにまとめ、全登録を表示します。黄色は修正フォームから承認・反映された枠です。配布前に、文字の大きさ、氏名、競技、ページ数、各クラスが1ページに収まっていることを目視確認してください。

## 技術スタック

- **フォーム**: Google Forms
- **データ・帳票**: Google Sheets
- **自動化**: Google Apps Script
- **ファイル保管**: Google Drive（体育祭スタッフ共有Gmailアカウントで所有し、必要な相手だけに共有）
- **外部API**: 原則使用しない。個人情報を含まないフォーム設問作成だけGoogle Forms APIを使用

```text
├── 種目別名簿スプレッドシート
├── クラス別・招集順選手名簿スプレッドシート
└── 当日変更用スプレッドシート
```

## 運用手順

1. `競技設定`を確認し、通常登録フォームと修正申請フォームを生成する。
2. フォーム受付後、管理画面の「警告○件」「エラー○件」を確認する。
3. 一覧から対象申請を開き、必要に応じて画面内修正・保留・却下を行う。同じクラスの回答が複数ある場合は、内容を並べて採用する1件を選ぶ。誤って却下した場合は`却下済み`から開き、理由を入力して確認待ちへ戻す。
4. 問題がなければ申請を承認する。
5. `選手登録管理` → `承認済みから選手名簿を作成`を選び、名簿の名前を入力する。
6. 表示された版名と保存先を確認し、`登録データ`と3種類の名簿が更新されたことを確認する。
7. 帳票を必要に応じて編集し、PDF化・印刷する。

## セキュリティ上の重要事項

- 実在の生徒マスターや名簿をLLMへ送信しない。
- GASからLLM APIを呼び出さない。`UrlFetchApp`はGoogle Forms APIによる設問作成だけに限定し、生徒マスター・回答・氏名・学籍番号の入力値を送信しない。
- 「リンクを知っている全員」共有を禁止する。
- 公開Webアプリとしてデプロイしない。
- ログや通知に不要な氏名を含めない。
- 開発には疑似生徒マスターのみを使用する。
